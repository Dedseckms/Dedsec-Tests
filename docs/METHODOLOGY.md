# Methodology: dedsec-v1

The public [methodology page](https://tests.dedseckms.ru/methodology) defines the exact CPU SHA-256, GPU xorshift32, RAM and disk workloads. Source lives in `src/Dedsec.Tests/Benchmarks.cs` and `GpuBenchmark.cs`. Warmup, payload size, worker count, units and elapsed time matter; results from changed workloads require a new suite version. CPU input bytes are generated by xorshift32 seed 0xDED; every SHA-256 result is checked against an independently computed golden digest. There is no composite score or claim that one workload predicts all applications.

GPU work is submitted only to a user-selected hardware DXGI adapter with D3D11 feature level 11.0. Each completed dispatch runs 65,536 lanes of 256 dependent xorshift32 iterations. GPU timestamps, guarded by a disjoint/frequency query, time the actual GPU workload. Batches adapt towards 50 ms and DXGI completion events avoid CPU polling sleeps. Every uint output is subsequently checked against a CPU reference. A separate child with a timeout and kill-on-close Job Object prevents continued GPU work after the parent exits. GPU command overhead is included; CPU sleep/wait time is excluded. The recorded GPU duration is accumulated hardware time; the sampling loop runs for five wall seconds. This is not a render/VRAM/game-FPS test.

Disks are tested through an owned temporary file, with unbuffered/write-through I/O and 4096-byte aligned buffers. Reads verify all bytes. Device caches, filesystem/encryption and the small working set still matter. A requested system volume uses an accessible user temporary directory on that volume; a selected directory can be used on other volumes. No raw disk or existing user file is written. The listed physical-disk inventory is not automatically equated with the selected logical volume.

Diagnostics are bounded observations, not a guarantee of health. WMI unavailability is distinct from an all-clear. Event reader queries seven days of System/Application Critical/Error/Warning events, up to 1,200 per channel or eight seconds, and groups source + Event ID. Explanations are curated possible causes and next steps. They do not assign hardware blame from a single event. Event messages can contain local personal paths and are never part of the publication payload.

The local decoder distinguishes Win32/HRESULT from BSOD STOP codes. Unknown providers/codes receive an explicit context-needed explanation instead of an invented definitive repair.
